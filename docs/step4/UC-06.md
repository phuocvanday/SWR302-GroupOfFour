| **Primary Actor** | Gym Owner |
| **Secondary Actors** | QR Service; SMS Service |
| **Trigger** | Gym Owner selects a paid **INACTIVE** membership and chooses **Activate**, usually right after completing UC-05. |
| **Description** | Gym Owner activates a membership after full payment is recorded. The system sets status to **ACTIVE**, computes the end date, generates a unique membership QR code, and notifies the Customer by SMS. |
| **Preconditions** | 1. Gym Owner has successfully logged in (UC-02). 2. The target Membership exists with status **INACTIVE**. 3. The full package fee for that Membership has been recorded as paid (BR-02). |
| **Post conditions** | 1. Membership status is **ACTIVE**. 2. `end_date` is set to activation date + package `DurationMonths` (BR-03), end of day UTC+7. 3. Exactly one membership QR is generated and linked (BR-04) via «include» **Generate QR Code**. 4. An activation SMS is sent or queued to the Customer. 5. If the use case fails before success, the membership remains **INACTIVE** and has no usable check-in QR. |
| **Normal Flow** | 1. Gym Owner opens the list of memberships pending activation (**INACTIVE** + paid). 2. System displays candidates with Customer name, package, fee status, and created date. 3. Gym Owner selects one Membership and chooses **Activate**. 4. System shows membership details and payment confirmation summary. 5. Gym Owner confirms activation. 6. System verifies that the fee is fully paid (BR-02) and sets membership status to **ACTIVE**. 7. System computes and stores `end_date` = activation date + `DurationMonths` (BR-03). 8. System «include» **Generate QR Code**: requests QR Service to create a unique QR payload for this membership (BR-04). 9. QR Service returns the QR token/image; System stores and links it to the membership. 10. System composes an activation message and sends it to SMS Service with the Customer phone number. 11. SMS Service accepts the message for delivery. 12. System displays activation success (Membership ID, validity period, QR preview/print option). |
| **Alternative Flows** | 1. **Fee not fully paid**: At Normal Flow step 6, if payment is incomplete, System blocks activation, shows the outstanding amount (BR-02), and the membership stays **INACTIVE**. 2. **Cancel confirmation**: At step 5, if Gym Owner cancels, System leaves the membership unchanged and the use case ends. 3. **Resend SMS / reprint QR** (optional operations): If the membership is already **ACTIVE**, System allows resend SMS or reprint QR without changing status or end date. |
| **Exceptions** | 1. **QR Service failure**: At steps 8–9, if QR Service fails or times out, System rolls back to **INACTIVE** so that no **ACTIVE** membership exists without a QR (BR-04), shows an error, and does not send SMS; Owner may retry. 2. **SMS Service failure**: At steps 10–11, if SMS fails after **ACTIVE** + QR succeeded, System keeps **ACTIVE** and QR, warns that SMS failed, and offers **Resend SMS** (partial success). 3. **Concurrent update**: At step 6, if another session already changed the membership so it is no longer **INACTIVE**, System refreshes status and aborts with a conflict message. |
| **Priority** | High |
| **Frequency of Use** | High — typically once per successful counter registration (same order of magnitude as UC-05). |
| **Business Rules** | BR-01: Only Gym Owner may activate membership. BR-02: Activation requires full fee recorded. BR-03: End date = activation date + `DurationMonths`. BR-04: Each **ACTIVE** membership has exactly one QR; QR is invalid when status ≠ **ACTIVE**. |
| **Other Information** | Related diagrams: UCD Overview / Membership; AD-03 Activate Membership at counter; SMD-01 Membership. Wireframe: SCR-06 (Step 5). Supporting relation: «include» Generate QR Code. Derived FRs: FR-06-01…FR-06-05. |
| **Assumptions** | Customer phone number stored for the membership is valid for SMS delivery. QR Service is reachable during activation. AS-02: one stable QR per **ACTIVE** membership until expiry/reissue. |
