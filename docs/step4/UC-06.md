# UC-06 — Activate Membership

> Package: Membership · Priority: **High** · SRS §3 (fully dressed)

## 1. Identification

| Field | Content |
|-------|---------|
| **ID & Name** | UC-06: Activate Membership |
| **Primary actor** | Gym Owner |
| **Secondary actor(s)** | QR Service; SMS Service |
| **Description** | After full payment is recorded, Gym Owner activates an **INACTIVE** membership: system sets status **ACTIVE**, computes end date, generates a unique membership QR, and notifies the Customer by SMS. |
| **Trigger** | Gym Owner selects an unpaid-complete / ready membership and chooses **Activate**, usually right after UC-05. |
| **Preconditions** | PRE-1: Gym Owner is logged in (UC-02). PRE-2: Target Membership exists with status **INACTIVE**. PRE-3: Full package fee is recorded as paid (BR-02). |
| **Postconditions (success)** | POST-1: Membership status = **ACTIVE**. POST-2: `end_date` = activation date + package `DurationMonths` (BR-03). POST-3: Exactly one membership QR is issued and linked (BR-04) via **«include» Generate QR Code**. POST-4: Activation SMS is sent (or queued) to Customer. |
| **Postconditions (failure)** | Membership remains **INACTIVE**; no usable check-in QR for this membership. |
| **Frequency** | Same order of magnitude as UC-05 (each paid registration is activated once). |
| **Business rules** | BR-01, BR-02, BR-03, BR-04 |
| **Related diagrams / screens** | UCD Overview / Membership; AD-03 Activate Membership at counter; SMD-01 Membership; Wireframes SCR-06 (Bước 5) |
| **Assumptions** | Customer phone number is valid for SMS; QR Service is reachable during activation. |

## 2. Main success scenario (Normal flow)

**06.0 Activate paid membership and issue QR**

1. Gym Owner opens the list of memberships pending activation (INACTIVE + paid).
2. System displays candidate memberships with Customer name, package, fee status, and created date.
3. Gym Owner selects one Membership and chooses **Activate**.
4. System shows membership details and payment confirmation summary.
5. Gym Owner confirms activation.
6. System verifies fee is fully paid (BR-02); if OK, sets membership status to **ACTIVE**.
7. System computes and stores `end_date` = activation date + `DurationMonths` (BR-03), end of day UTC+7.
8. System **«include» Generate QR Code**: requests QR Service to create a unique QR payload for this membership (BR-04).
9. QR Service returns the QR token/image; System stores and links it to the membership.
10. System composes an activation message and sends it to SMS Service with Customer phone number.
11. SMS Service accepts the message for delivery.
12. System displays activation success (Membership ID, validity period, QR preview / print option).

## 3. Alternative flows

**06.1 Fee not fully paid**  
At step 6, if payment is incomplete:  
1. System blocks activation and shows the outstanding amount (BR-02).  
2. Gym Owner returns to payment collection (related to UC-05 / renew payment) or ends the use case.  
3. Membership stays **INACTIVE**.

**06.2 Owner cancels confirmation**  
At step 5, if Gym Owner cancels:  
1. System leaves membership unchanged.  
2. Use case ends.

**06.3 Reprint / resend after prior success (optional operational path)**  
If membership is already ACTIVE and Owner only needs to resend SMS or reprint QR:  
1. System allows resend/reprint without changing status or end date.  
2. Use case ends after notification/print.  
*(May be documented as a separate brief UC later; kept here as alt for counter operations.)*

## 4. Exception flows

**06.0.E1 QR Service failure**  
At step 8–9, if QR Service fails or times out:  
1. System rolls back activation **or** keeps a compensating transaction policy: prefer rollback to **INACTIVE** so no ACTIVE membership exists without QR (BR-04).  
2. System shows an error; Gym Owner may retry.  
3. SMS is not sent.

**06.0.E2 SMS Service failure**  
At step 10–11, if SMS fails after ACTIVE + QR succeeded:  
1. System keeps ACTIVE membership and QR (core goal achieved).  
2. System warns that SMS failed and offers **Resend SMS**.  
3. Use case may end with partial success (activation OK, notify pending).

**06.0.E3 Concurrent update / membership no longer INACTIVE**  
At step 6, if another session already activated or cancelled the record:  
1. System refreshes status and aborts with a conflict message.  
2. Use case ends.

## 5. Special requirements / BR

- BR-01: Only Gym Owner may activate.  
- BR-02: Activation requires full fee recorded.  
- BR-03: End date computation from activation + duration.  
- BR-04: One QR per ACTIVE membership; QR invalid when status ≠ ACTIVE.  
- Supporting UC: **Generate QR Code** («include»).  
- Functional requirements to derive in SRS §3.x.5: e.g. FR-06-01 set ACTIVE; FR-06-02 compute end_date; FR-06-03 generate QR; FR-06-04 send SMS; FR-06-05 reject unpaid activation.
