# UC-12 — Confirm / Reject PT Booking

> Issue: #21 · Branch: `step4/tuan-uc-11-12`

## 1. Use case summary

| Item | Description |
|------|-------------|
| Use case ID | UC-12 |
| Primary actor | Personal Trainer |
| Secondary actors | SMS Service, Payment Gateway |
| Goal | Allow an Approved Personal Trainer to respond to a Pending PT booking within 24 hours. |
| Priority | High |
| Related business rules | BR-07, BR-08, BR-09 |

## 2. Preconditions

1. The Personal Trainer is authenticated.
2. The Personal Trainer account is in `Approved` status.
3. A `Pending` PT booking belongs to the Personal Trainer.
4. The booking has not expired or been cancelled.

## 3. Postconditions

### Confirm outcome

- The booking status is changed to `Confirmed`.
- The Customer is notified.
- The booking becomes eligible for Training Session scheduling.

### Reject outcome

- The booking status is changed to `Rejected`.
- A rejection reason is stored.
- The Customer is notified.
- A refund request is initiated when a successful payment exists.

## 4. Main success scenario

1. The system notifies the Personal Trainer of a new Pending booking.
2. The Personal Trainer opens the Pending booking list.
3. The Personal Trainer selects a booking.
4. The system displays the Customer, PT package, preferred time, booking time, payment status, and notes.
5. The Personal Trainer chooses `Confirm`.
6. The system verifies that the booking is still Pending, belongs to the current Personal Trainer, and is within the response time limit.
7. The system changes the booking status to `Confirmed`.
8. The system records the response time and sends a confirmation notification to the Customer.

## 5. Alternative flows

### A1. Personal Trainer rejects the booking

1. At step 5, the Personal Trainer chooses `Reject`.
2. The system requires a rejection reason.
3. The Personal Trainer enters the reason and submits the decision.
4. The system verifies that the booking is still Pending.
5. The system changes the booking status to `Rejected`.
6. The system initiates a refund when a successful payment exists.
7. The system sends the rejection reason and status to the Customer.

### A2. Booking has already been processed

1. At step 6, the system detects that the booking is no longer Pending.
2. The system displays the current status.
3. The system does not overwrite the existing decision.

## 6. Exceptions

### E1. Response deadline has passed

1. The system detects that the Pending booking has exceeded 24 hours.
2. The system changes the booking status to `Cancelled` according to the timeout policy.
3. The system initiates a refund when applicable.
4. The system notifies the Customer and the Personal Trainer.

### E2. Rejection reason is missing

1. The Personal Trainer submits `Reject` without a reason.
2. The system displays a validation error.
3. The system does not change the booking status.

### E3. Refund cannot be completed immediately

1. The Payment Gateway rejects or delays the refund request.
2. The system records the refund as `Pending` and creates an operational alert.
3. The booking remains `Rejected`; the refund is processed through reconciliation.

## 7. Business rules and notes

- BR-07: only an Approved Personal Trainer may process the booking.
- BR-08: the Personal Trainer must respond within 24 hours.
- BR-09: rejecting a paid booking requires a refund process; a rejection reason is mandatory.
- Confirm and Reject are alternative flows in UC-12, not separate `<<extend>>` use cases.
