# UC-05 — Register Membership (at Counter)

> Issue: [#20](https://github.com/phuocvanday/SWR302-GroupOfFour/issues/20) · Branch: `step-4` · Author: Phước  
> Package: Membership · Priority: **High** · SRS §3 (fully dressed)

## 1. Identification

| Field | Content |
|-------|---------|
| **ID & Name** | UC-05: Register Membership (at Counter) |
| **Primary actor** | Gym Owner |
| **Secondary actor(s)** | Payment Gateway (optional for card/transfer); Customer (provides personal data at counter) |
| **Description** | Gym Owner creates a membership record for a Customer at the gym counter: selects package, collects payment (or records cash), and leaves the membership in **INACTIVE** until activation (UC-06). |
| **Trigger** | A walk-in Customer requests a membership package at the counter, or Gym Owner starts “Register Membership”. |
| **Preconditions** | PRE-1: Gym Owner is logged in (UC-02). PRE-2: At least one Membership Package is published/active in the catalog (UC-23). PRE-3: Customer is present at the counter (or reachable by phone for data confirmation). |
| **Postconditions (success)** | POST-1: A Membership record exists with status **INACTIVE**. POST-2: Fee amount and payment attempt (if any) are recorded. POST-3: Customer profile is created or linked if new/existing. |
| **Postconditions (failure)** | No new ACTIVE membership; incomplete draft may be discarded or kept as unpaid/INACTIVE without QR. |
| **Frequency** | High during opening hours (~tens of registrations/day at a busy site). |
| **Business rules** | BR-01, BR-02 |
| **Related diagrams / screens** | UCD Overview / Membership; AD-03 (with UC-06); Wireframes SCR-05 (Bước 5) |
| **Assumptions** | Cash/transfer confirmation may be entered manually by Owner; online gateway is optional. QR is **not** issued in this UC (only in UC-06). |

## 2. Main success scenario (Normal flow)

**05.0 Register membership at counter and record payment**

1. Gym Owner selects **Register Membership**.
2. System displays the registration form and the list of available Membership Packages.
3. Gym Owner identifies the Customer (search by phone/email or enter new Customer details: full name, phone, email).
4. System validates contact data format and shows whether the Customer already exists.
5. Gym Owner selects a Membership Package.
6. System calculates the payable fee and displays package duration and total amount.
7. Gym Owner confirms the registration summary.
8. System creates a Membership record linked to the Customer and package with status **INACTIVE** (BR-02: not ACTIVE yet).
9. Gym Owner initiates payment collection (cash recorded in GMS, or online via Payment Gateway — **«include» Process Payment** when gateway is used).
10. System records payment as received (full amount) or marks payment pending according to the chosen method.
11. System displays success with Membership ID and prompts Gym Owner to proceed to **Activate Membership (UC-06)** when fee is fully paid.

## 3. Alternative flows

**05.1 Apply promo code («extend» Apply Promo Code → PromoApplication)**  
At step 6, if the Customer presents a promo code:  
1. Gym Owner enters the promo code.  
2. System validates the code and recalculates the fee.  
3. Resume at step 7 with the discounted amount.

**05.2 Existing Customer found**  
At step 4, if phone/email already belongs to a Customer:  
1. System shows the existing profile.  
2. Gym Owner confirms using that profile (no duplicate account).  
3. Resume at step 5.

**05.3 Cash payment only (no Payment Gateway)**  
At step 9, if payment is cash/transfer confirmed offline:  
1. Gym Owner marks “Paid in full at counter” and enters reference note.  
2. System stores the payment record without calling Payment Gateway.  
3. Resume at step 11.

**05.4 Owner cancels before confirm**  
At step 7, if Gym Owner cancels:  
1. System discards the uncommitted form.  
2. Use case ends with no new membership.

## 4. Exception flows

**05.0.E1 Payment Gateway failure**  
At step 9–10, if the gateway returns failure or timeout:  
1. System displays payment failure and keeps membership **INACTIVE** / unpaid.  
2. Gym Owner may retry payment or end the use case.  
3. No activation is offered until fee is fully recorded (BR-02).

**05.0.E2 Persistence / system error**  
At step 8, if the system cannot save the membership:  
1. System displays an error and does not confirm success.  
2. Use case ends; Owner may retry later.

**05.0.E3 Invalid or expired promo**  
During 05.1, if the promo code is invalid/expired:  
1. System rejects the code and keeps the original fee.  
2. Resume at step 6 or cancel per Owner.

## 5. Special requirements / BR

- BR-01: Only authenticated Gym Owner may register membership at counter.  
- BR-02: Membership must not become **ACTIVE** until full fee is recorded (activation is UC-06).  
- Supporting UC: **Process Payment** («include» when online payment is used).  
- Extending UC: **Apply Promo Code** at extension point **PromoApplication**.  
- Functional requirements to derive in SRS §3.x.5: e.g. FR-05-01 create INACTIVE membership; FR-05-02 link Customer; FR-05-03 record payment; FR-05-04 apply promo (optional).
