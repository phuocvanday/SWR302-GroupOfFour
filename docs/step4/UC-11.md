# UC-11 — Book a PT Package

> Issue: #21 · Branch: `step4/tuan-uc-11-12`

## 1. Use case summary

| Item | Description |
|------|-------------|
| Use case ID | UC-11 |
| Primary actor | Customer |
| Secondary actors | Payment Gateway, SMS Service, Personal Trainer |
| Goal | Allow a Customer to book a PT package and complete the required online payment. |
| Priority | High |
| Related business rules | BR-06, BR-08 |

## 2. Preconditions

1. The Customer is authenticated.
2. The Customer has an ACTIVE membership with at least one valid day remaining.
3. The selected Personal Trainer has an Approved account.
4. The selected PT package is active and available for booking.

## 3. Postconditions

### Success guarantee

- A PT booking is created with status `Pending`.
- The payment result is recorded.
- The booking request is sent to the selected Personal Trainer.
- The Customer receives an in-app/SMS notification containing the booking status.

### Minimal guarantee

- No booking is marked `Confirmed` unless the payment result is successful and the state transition is valid.
- Failed or uncertain payment results are recorded for reconciliation.

## 4. Main success scenario

1. The Customer opens an Approved Personal Trainer's profile.
2. The Customer selects an available PT package.
3. The system displays the package name, number of sessions, price, validity period, and available scheduling information.
4. The Customer selects a preferred date/time and optionally enters a note.
5. The Customer confirms the booking details.
6. The system validates the membership, PT account, package, requested time, and current price.
7. The system creates a pending payment request and sends it to the Payment Gateway.
8. The Payment Gateway returns a successful result.
9. The system records the successful payment and creates the PT booking with status `Pending`.
10. The system sends the booking request to the Personal Trainer.
11. The system sends an in-app/SMS notification to the Customer and displays the booking reference.

## 5. Alternative flows

### A1. Customer enters a valid promotion code

1. At step 4, the Customer enters a promotion code.
2. The system validates the code and recalculates the payable amount.
3. The Customer confirms the updated amount.
4. The use case continues at step 6 of the main scenario.

### A2. Payment is declined

1. At step 8, the Payment Gateway returns `Fail`.
2. The system records the failed payment.
3. The system does not send a booking request to the Personal Trainer.
4. The system informs the Customer and allows the Customer to retry or cancel.

### A3. Customer cancels before payment

1. Before step 8, the Customer cancels the operation.
2. The system cancels the pending payment request, if one exists.
3. The system does not create a valid PT booking.

## 6. Exceptions

### E1. Payment Gateway timeout or uncertain response

1. At step 8, the Payment Gateway does not respond within the configured timeout.
2. The system marks the payment as `Pending` or `Unknown` for reconciliation.
3. The system does not treat the booking as paid or `Confirmed` automatically.
4. The system shows the Customer that the payment is being checked.

### E2. Package or schedule becomes unavailable

1. At step 6, the system detects that the package is inactive, unavailable, or the requested time is no longer valid.
2. The system rejects the request and displays the reason.
3. The Customer must select another package or time.

## 7. Business rules and notes

- BR-06: the Customer must have an ACTIVE membership to book a PT package.
- BR-08: the PT must respond to a Pending booking within 24 hours.
- Confirm/Reject is handled by UC-12 and is not an `<<extend>>` relationship.
